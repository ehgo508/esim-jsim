# 6장. 내 eSIM 상태와 사용량 조회 (006)

## 1. 이 기능에서 배우는 것

느리고 호출 제한이 있는 외부 시스템의 데이터를 사용자에게 빠르고 안정적으로 보여주는 방법(캐시, 장애 시 대체 응답), 그리고 "시간"이 들어간 로직을 테스트하는 방법.

## 2. 알아야 할 개념

| 개념 | 설명 | 왜 필요한가 |
|------|------|------------|
| 사용량의 출처 | 폰이 아니라 현지 통신사가 집계해 공급사로 넘긴 값. 몇 분에서 몇 시간 늦을 수 있다 | `syncedAt`을 보여주는 이유 |
| 데이터 전용 요금제 | 여행 eSIM 대부분은 통화·문자가 없다 | `voice`, `sms`가 `null`인 경우 |
| null과 0의 차이 | null은 "해당 없음", 0은 "값이 0" | 통화 미포함과 통화 0분 사용의 구분 |
| 캐시 | 한 번 가져온 값을 저장해 두고 재사용 | 공급사 호출 줄이기 |
| TTL (유효 시간) | 캐시를 믿을 수 있는 시간. 지나면 다시 가져온다 | 5분 규칙 |
| Rate limit | API가 일정 시간에 허용하는 호출 횟수 | 실제 공급사에는 거의 항상 있다 |
| Fallback | 주 경로가 실패했을 때의 대체 동작 | 공급사 장애 시 마지막 값 응답 |
| Stale 데이터 | 오래되어 최신이 아닐 수 있는 데이터 | `stale = true` 표시 |
| `java.time` | `Instant`(UTC 시점), `Duration`(시간 길이), `ZonedDateTime`(시간대 포함) | 만료 시각, 남은 일수 |
| `Clock` | "지금"을 알려주는 객체. 테스트에서 고정할 수 있다 | 5분 경계 테스트 |
| UTC와 시간대 | 서버는 UTC로 저장하고 화면에서 현지 시간으로 변환 | 여행 서비스라 시간대가 여러 개 |
| 단조 상태 전이 | 상태가 한 방향으로만 진행 | 공급사 응답이 늦게 와도 상태가 뒤로 가지 않게 |
| DTO 프로젝션 / fetch join | 목록에 필요한 연결 데이터를 한 번에 가져오기 | 내 eSIM 목록의 요금제·국가 |
| upsert | 있으면 수정, 없으면 삽입 | eSIM당 스냅샷 1건 유지 |

## 4. 구현 순서와 힌트

| 작업 | 힌트 |
|------|------|
| T002 목록 쿼리 | 상태 그룹 정렬은 DB에서 할 수도, 자바에서 할 수도 있다. eSIM이 사용자당 몇 개 안 되므로 어느 쪽이 단순한지 판단한다 |
| T006 가짜 사용량 | "발급 후 1시간마다 100MB" 같은 단순한 규칙이면 충분하다. 총량을 넘는 값도 일부러 만들 수 있게 해 두면 경계 테스트에 쓸 수 있다 |
| T008 syncStatus | enum에 순서 값을 두거나 `ordinal()`을 쓰는 방법이 있다. 2장에서 배운 ORDINAL의 위험과 무엇이 다른지 생각해 본다 |
| T009 계산 로직 | 계산을 DTO의 정적 메서드나 별도 클래스에 모으면 Spring 없이 테스트할 수 있다. `daysLeft` 올림은 정수 나눗셈의 함정을 조심한다 |
| T010 먼저 단순하게 | 캐시 없이 매번 공급사를 부르는 버전을 먼저 완성하고 테스트를 통과시킨다. 그다음 Phase 3에서 5분 규칙을 추가한다 |
| T012 Clock | `Clock.systemUTC()`를 Bean으로 등록하고, 테스트에서는 `Clock.fixed(...)`로 교체한다. 코드 어디에도 `Instant.now()`를 인자 없이 쓰지 않는다 |
| T014 fallback | 공급사 호출을 try-catch로 감싸는 위치가 중요하다. 예외를 삼키더라도 로그는 남긴다 |
| T017 전체 흐름 | 팀원이 아닌 사람에게 시켜 보고, 막히는 곳을 적는다. 그 목록이 다음 개선 과제다 |

## 5. 스스로 점검할 질문

- 사용량 화면의 숫자가 폰 설정의 숫자와 다를 수 있는 이유는?
- 통화 미포함 요금제에서 `voice`를 0이 아니라 `null`로 주는 이유는?
- 캐시 시간을 5분에서 1시간으로 늘리면 무엇이 좋아지고 무엇이 나빠지는가?
- 공급사가 죽었을 때 에러 화면 대신 오래된 값을 보여주는 것이 더 나은 이유는? 그때 사용자에게 꼭 알려야 하는 것은?
- `Instant.now()`를 직접 쓰면 "6분 뒤" 테스트를 어떻게 해야 하는가? `Clock`을 쓰면 어떻게 달라지는가?
- 공급사가 `ACTIVE`를 알려준 뒤, 늦게 도착한 `INSTALLED` 응답을 그대로 반영하면 어떤 일이 생기는가?
- 만료된 eSIM의 사용량을 공급사에 다시 묻지 않는 이유는?
- 사용자 1,000명이 동시에 사용량 화면을 열면 공급사 호출은 최대 몇 번인가?

## 6. 흔한 실수

- `LocalDateTime`으로 시각을 저장해 시간대 정보가 사라진다. 시점은 `Instant`로 다룬다.
- 남은 양 계산에서 음수가 나온다.
- 5분 경계 테스트를 `Thread.sleep`으로 한다. 테스트가 느리고 불안정해진다.
- fallback에서 예외를 삼키고 로그를 남기지 않아 장애를 아무도 모른다.
